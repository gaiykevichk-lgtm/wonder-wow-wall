## 05.05.2026

### Конфигуратор панелей: переосмысление каталога и карточки товара в Apple-style

Каталог и страница товара полностью переработаны по модели Apple-конфигуратора. Вместо плоского списка накладок-дизайнов продукт теперь строится вокруг иерархии «Форма → Текстура → Цвет»: пользователь сначала выбирает геометрию панели (волна, гексагон, треугольник и т. д.), затем материал (бетон, дерево, мрамор) и цветовой вариант, а на экране в реальном времени отображается фотография именно этой комбинации. Визуальный референс — конфигуратор MacBook Air на apple.com: крупное превью слева, компактная панель выбора справа, sticky на скролле.

**Новая иерархия данных:**
- `Design` — теперь означает геометрическую форму (slug: wave, hexagon, triangle). Каталог показывает белые силуэты форм на светлом фоне, от цены «от N ₽»
- `Texture` — материал/текстура панели с превью-свотчем и slug'ом (concrete, wood, marble)
- `TextureColor` — конкретный цвет в рамках текстуры: hex, swatch-изображение, название («Серый бетон», «Тёплый дуб»)
- `VariantImage` — загруженная фотография конкретной комбинации (форма + текстура + цвет); уникальная по тройке (design_id, texture_id, color_id)

Это изменение не ломает исторические заказы: поля `Design.colors` сохранены как legacy, старые `OrderItem` хранят текстуру и цвет в текстовых полях и рендерятся по-прежнему.

**Как работает конфигуратор на карточке товара:**
1. При открытии страницы — единый запрос `GET /api/designs/{id}/full-config` возвращает форму, все текстуры, цвета и пути к variant-images без N+1
2. По умолчанию выбрана первая текстура, первый цвет, первый размер
3. При смене текстуры — обновляются доступные цвета, автоматически выбирается первый
4. При смене цвета — превью плавно меняется (fade-transition); если variant-image не загружен — fallback на белый силуэт формы
5. При смене размера — пересчитывается итоговая цена (base_price зависит от размера: 890 / 1490 / 2490 ₽ + цена дизайна)
6. Sticky-панель CTA на мобильных (bottom bar ≤860px) — цена и кнопка «В корзину» всегда видны

### Модель данных и миграция БД

Alembic-миграция `018_create_textures_and_variants.py` добавляет три новые таблицы и два ALTER:

- `textures` (id, name, slug UNIQUE, swatch_image, sort_order, is_active, created_at)
- `texture_colors` (id, texture_id FK CASCADE, name, hex, swatch_image, sort_order, is_active, created_at)
- `variant_images` (id, design_id FK, texture_id FK, color_id FK, image_path, created_at; UNIQUE на тройку)
- `designs.preview_image VARCHAR(500) DEFAULT ""` — путь к белому силуэту формы для каталога
- `order_items.texture_name / texture_id / color_id DEFAULT ""` — для хранения атрибутов нового флоу в заказе

Все новые колонки nullable / server_default="" — существующие записи не затронуты. FK `variant_images` → RESTRICT (текстуру с изображениями нельзя удалить), FK `texture_colors.texture_id` → CASCADE (удаление текстуры каскадно удаляет её цвета).

Репозитории и use cases реализованы для всех трёх новых сущностей: CRUD-операции, валидация уникальности slug, hex-валидация на доменном и API-уровне (pattern `^(#[0-9A-Fa-f]{6})?$`), guard от удаления текстуры с изображениями (409 Conflict).

### Новые API-эндпоинты

**Публичные:**
- `GET /api/designs` — расширен полями `preview_image` и `default_colors` (первые 4 цвета из первой текстуры, batch-запрос без N+1)
- `GET /api/designs/{id}/full-config` — форма + все текстуры + цвета + variant-image paths одним запросом
- `GET /api/designs/{id}/textures` — текстуры с цветами; фильтруются текстуры без активных цветов
- `GET /api/designs/{id}/variant-image?texture_id=…&color_id=…` — путь к изображению комбинации
- `GET /api/textures` и `GET /api/textures/{id}/colors` — публичный справочник текстур

**Админские:** полный CRUD текстур, цветов и variant-images под guard'ом роли `admin`:
- `GET/POST /api/admin/textures`, `PATCH/DELETE /api/admin/textures/{id}`
- `GET/POST /api/admin/textures/{id}/colors`, `PATCH/DELETE /api/admin/texture-colors/{id}`
- `GET/POST /api/admin/variant-images`, `DELETE /api/admin/variant-images/{id}`

Все admin-эндпоинты: 401 без токена, 403 с customer-токеном, slug-конфликт 409 (включая guard «не конфликтовать с самим собой» при PATCH), удаление текстуры с изображениями 409.

## 26.04.2026

### Фирменная рамка Wonder Wow Wall в ключевых интерфейсах

В продукт внедрён фирменный «сертификатный» каркас, который заказчик использует на печатных материалах: тонкая двойная линейка по периметру и логотип Wonder Wow Wall, врезанный во внутреннюю рамку в правом нижнем углу. Это сильный, но «громкий» элемент — поэтому добавлен только туда, где пользователь переживает «момент гордости» или продукт показывает что-то готовое целиком, и НЕ применён к плотным таблицам, спискам и формам, чтобы не превращать интерфейс в открытку.

**Где появляется рамка:**
- **Страница «Спасибо за заказ»** — после оформления покупки вместо короткого всплывающего сообщения и редиректа теперь открывается отдельный экран в фирменной рамке: номер заказа, итоговая сумма, понятный шаг «Что дальше», кнопки «Мои заказы» и «Продолжить покупки». Рамка плавно появляется при первом показе.
- **Окно «Подписка оформлена!»** — финальный шаг модалки подписки получил рамку с логотипом, — момент активации тарифа теперь читается как welcome-сертификат, а не служебное «готово».
- **Карточки сохранённых проектов в личном кабинете** (`/account/projects`) — каждая карточка проекта обрамлена компактной (без логотипа) версией двойной линейки. Список ощущается как «галерея моих работ» вместо файлового списка.
- **Шапка дашборда админки** — заголовок «Дашборд» и переключатель периода теперь живут внутри рамки с логотипом, превращая верхний блок страницы в «обложку отчёта» (плотные виджеты дальше остаются нетронутыми).

**Один компонент, две версии:**
- `<BrandedFrame variant="full">` — рамка с логотипом и двумя короткими «штрихами» по бокам, имитирующими разрыв внутренней линейки вокруг логотипа (как в исходнике заказчика). Используется на success-страницах и hero-блоке дашборда.
- `<BrandedFrame variant="compact">` — только двойная линейка без логотипа, для карточек и тайлов в коллекциях.
- Оба варианта берут цвет из темы (по умолчанию фирменный тёмно-серый `#2D2D2D`), масштабируются под любой размер контейнера и любую пропорцию, не выкидывают логотип за пределы рамки на узких экранах.

**Деликатность к пользователю:**
- Анимация появления рамки на success-страницах — плавная, с уважением к системной настройке `prefers-reduced-motion` (если у пользователя включено «уменьшать анимации» — рамка появляется без эффекта).
- Логотип в рамке помечен `aria-hidden` — скринридерам не зачитывается дублирующий «Wonder Wow Wall», так как название компании уже звучит в шапке.
- Внутренняя линия аккуратно маскируется ровно под областью логотипа (а не под всей нижней частью рамки) — на нестандартных фонах не появится белая полоса.

**Что осталось за рамками этого релиза (буквально):** PDF-чек заказа и инструкция по монтажу с фирменной рамкой — в продукте пока нет инфраструктуры генерации PDF на сервере или клиенте. Это отложено в бэклог: при появлении PDF-генерации тот же `<BrandedFrame>` будет использоваться как макетный каркас для документа.

**Тесты:** 243 admin- + account-теста и 74 теста order/subscription/shared проходят без регрессий. `tsc --noEmit` чистый.

### Дашборд админки: 8 новых виджетов для операционной аналитики

MVP-дашборд из записи от 25.04 (4 KPI + revenue по дням + статусы заказов + топ дизайнов) расширен до полноценной операционной сводки. Добавлено восемь виджетов, закрывающих главные слепые зоны: подписочную монетизацию, конверсию заказов, висящие задачи и продуктовую аналитику использования инструментов.

**Подписки и MRR:**
- Карточки на втором ряду дашборда: число активных подписок, MRR (recurring revenue в ₽/мес), новые подписки за период, отток (churn %)
- Стек-бар «Подписки по планам»: распределение активных подписчиков между Стартовым / Популярным / Бизнес планами с процентами
- MRR считается как сумма цен текущих активных тарифов — изменение цены в админке отражается мгновенно в следующем обновлении дашборда

**Воронка заказов:**
- Виджет «Воронка заказов»: оформлен → подтверждён → в работе → доставлен → установлен
- Каждый этап показывает количество заказов и процент конверсии от верхнего этапа
- Отменённые и возвращённые заказы из воронки исключены — она показывает только «здоровый» поток

**Брошенные корзины:**
- Список сохранённых проектов конструктора с непустой стоимостью, владельцы которых не оформили заказ за выбранный период — proxy-метрика для retention-кампаний (живой корзины пока нет)
- Каждая строка: имя клиента, email, название проекта, число панелей, сумма, давность последней активности
- Сортировка по свежести — сверху недавние брошенные корзины, по которым ещё не поздно вернуть клиента

**Заказы — требуют внимания:**
- Таблица заказов, висящих дольше SLA: «оформлен» >24 ч, «подтверждён» >3 дней, «в работе» >7 дней
- Каждая строка: номер, клиент с email, статус, возраст в часах/днях/неделях, сумма, причина попадания в список
- Сортировка от худших к лучшим (самые старые сверху) — оператор сразу видит, что разруливать в первую очередь

**Использование конструктора и визуализатора:**
- Четыре мини-карточки: число сессий конструктора, число проектов в фоторедакторе, число вовлечённых уникальных пользователей и конверсия в заказ (%)
- «Вовлечённый» = создал хотя бы один проект в любом из инструментов; «конвертировался» = из вовлечённых оформил заказ за тот же период
- Помогает оценить, окупаются ли «дорогие» фичи (конструктор и фоторедактор стен)

**Размеры панелей:**
- Парный bar-chart по трём размерам (30×30, 30×60, 60×60 см): количество проданных штук и выручка
- Учитывает разные форматы записи `size_key` (короткая «30×30» и длинная «300×300») — везде показывает единый человекопонятный лейбл

**Топ городов:**
- Горизонтальный бар: 5 городов с наибольшей выручкой за период
- В каждой строке отображается выручка; сортировка от большего к меньшему. Заказы без указанного города схлопываются в строку «Не указан»
- Помогает планировать логистику и таргетинг рекламы

**Регистрации vs заказы:**
- Совмещённый линейный график по дням: новые регистрации (синяя линия) поверх новых заказов (зелёная линия)
- В заголовке карточки — итоги периода: «N регистраций · M заказов»
- Видно лаг между притоком трафика и активацией: всплески регистраций без последующих заказов = проблема с onboarding-ом или продуктом

**Сквозная функциональность:**
- Все восемь виджетов реагируют на единый переключатель периода (7 / 30 / 90 дней) — данные перерисовываются без перезагрузки
- У каждого виджета продумано пустое состояние: за выбранный период нет данных — показывается понятная подсказка вместо пустого графика
- Скелетоны на загрузке во всех виджетах сохраняют сетку — страница не «прыгает» при появлении данных
- Все восемь приходят в одной API-ответке — фронтенд делает один запрос, не восемь

**Тесты:** 817 backend и 231 frontend admin-тест проходят. Покрыты: gap-filling временных рядов, исключение отменённых из воронки, формат человекопонятных лейблов размеров, защита от плана с нулевой ценой, корректность churn% при отсутствии активных подписок.

- Блокировка / разблокировка аккаунта (заблокированный не может войти — на форме логина показывается понятное сообщение, не «неверный пароль»)
- Выдача и снятие роли `admin`. Защита от снятия роли у последнего админа в системе (показывается ошибка «Нельзя оставить магазин без администратора»)

**Хранилище файлов:**
- Загрузка изображений из админки в общее файловое хранилище: превью дизайнов, фото панелей, баннеры
- Защита: лимит размера 10 МБ, проверка типа (только JPG / PNG / WebP), защита от вредоносных файлов
- Дубликаты не создаются: одинаковый файл, загруженный дважды, переиспользует существующую запись (по хэшу содержимого)

**Управление каталогом — категории и дизайны:**
- CRUD категорий с переключателем активности и подсчётом числа привязанных дизайнов
- Защита: нельзя удалить категорию, в которой есть дизайны (показывается «В категории N дизайнов — сначала перенесите или удалите»)
- CRUD дизайнов с фильтрацией по категории и поиском, превью загружается через файловое хранилище
- **Скрытие дизайна одним кликом** через инлайн-переключатель: дизайн остаётся в системе и в исторических заказах, но не виден на публичном сайте (и отдельный, и в списках); изменение фиксируется в аудит-логе
- Удаление дизайна автоматически чистит ссылки на него в подборках «с этим покупают»

**Управление панелями (физические SKU):**
- CRUD физических панелей: название, slug, размеры (мм), базовая цена, описание, фото, признак активности
- Фильтры таблицы — по статусу и поиску (название / slug), pagination — всё на сервере
- **Конструктор стен** теперь тянет цены панелей из админки через API: меняется цена в админке → пользователь видит обновление в течение 5 минут без релиза
- Если API недоступен — конструктор показывает цены из встроенного fallback-словаря, чтобы не падать офлайн

**Магазин — настройки, баннеры, тарифы:**
- Раздел из трёх вкладок (Настройки / Баннеры / Тарифы), активная вкладка сохраняется в URL
- **Настройки**: цена накладки, цена монтажа, минимальный заказ, лимит рекомендаций. Изменения видны на витрине через ≤5 минут (TTL); подключены к карточкам товара, конструктору, личному кабинету, странице тарифов, фоторедактору стен и расчёту стоимости
- **Баннеры главной**: CRUD баннеров для трёх позиций (hero главной, верх каталога, футер) с заголовком, подзаголовком, картинкой, текстом и ссылкой кнопки, приоритетом и переключателем активности; на публичной витрине отображаются по приоритету (меньше — выше), скрытые баннеры не показываются
- **Тарифы подписок**: цены и параметры тарифов (стартовый / популярный / бизнес и любые свои) теперь редактируются из админки без релиза. Защита от удаления: тариф с активными подписчиками удалить нельзя — придёт ошибка «N активных подписок»; для вывода тарифа из продажи — переключатель активности (исторические подписки продолжают работать)

**Аудит-лог:**
- Каждое критичное действие админа записывается: блокировка пользователя, смена роли, изменение статуса заказа и возврат, добавление комментария к заказу, удаление дизайна / панели, изменение настроек магазина, добавление и удаление подборки рекомендаций, переключение публикации дизайна, удаление баннера, удаление тарифа
- Раздел «Аудит» с фильтрами: по типу действия, по админу, по объекту (например, «всё про этого пользователя» или «всё про этот заказ»), по диапазону дат
- Каждая запись содержит IP-адрес, с которого пришло действие, и развёрнутый payload (что именно поменялось — например, «статус: оформлен → подтверждён»)

**Рекомендации «с этим покупают»:**
- Раньше блок на странице товара формировался клиентской эвристикой (другие дизайны той же категории) — теперь админ задаёт подборку вручную
- Раздел «Рекомендации» в админке: таблица всех подборок с фильтрами по типу источника, наличию подборки и поиском по id источника или любого таргета («где этот товар рекомендуется?»)
- Редактор подборки: добавление, удаление и перестановка целей кнопками «↑ ↓ ✕», валидация на самоссылку и дубли
- **Авто-предложения**: рядом с подборкой показываются heuristic-кандидаты (та же категория, по рейтингу) — добавляются одним кликом
- **Bulk-копирование**: «Скопировать рекомендации с другого товара» в режимах «Заменить» (полностью переписать) или «Дополнить» (добавить недостающие с дедупликацией)
- На карточке товара блок «Похожие товары» сначала показывает админскую подборку; при её отсутствии или при ошибке API — fallback на старую эвристику, чтобы блок никогда не был пустым
- Защита: если админ удалил дизайн или панель, ссылки на них автоматически исчезают из всех подборок (не остаётся «битых» рекомендаций)
- Конфликт-баннер в редакторе: если параллельно другой админ сохранил подборку и начался рефреш страницы — локальные правки не затираются, появляется предложение явно загрузить серверную версию

**Сквозная функциональность:**
- Все таблицы (заказы, пользователи, дизайны, панели, рекомендации, аудит-лог) — фильтры и пагинация в URL, переживают F5 и шарятся ссылкой
- Все формы создания / редактирования — через AntD Drawer с валидацией на стороне клиента + понятными inline-сообщениями на типичные ошибки сервера (slug занят, тариф используется, рекомендация ссылается сама на себя и т. д.)
- Все деструктивные действия (удалить, отозвать роль, очистить подборку) — через `<Popconfirm>` с явным подтверждением
- Загрузка фото и превью везде идёт через единый компонент с прогресс-баром и валидацией размера / типа

**Безопасность:**
- Все админ-эндпоинты под guard'ом роли `admin`: попытка анонимом — 401, попытка обычным пользователем — 403
- Кеш публичных эндпоинтов настроек магазина, баннеров и тарифов — 5 минут (CDN-friendly, отражает админские правки в пределах TTL)
- Защита от утечки скрытых сущностей: и список, и detail-эндпоинт публичного каталога не отдают неопубликованные дизайны / неактивные панели / неактивные тарифы / отключённые баннеры — даже при попытке угадать UUID

**Тесты:** 815 backend и 289 frontend тестов проходят — покрытие включает invariants доменных моделей, end-to-end CRUD каждого раздела, защиту от утечек публичных эндпоинтов, audit-retrofit, bulk-операции, конфликт-сценарии редактора рекомендаций и регрессии на смежные потоки (каталог, конструктор, страница тарифов, фоторедактор стен).

### Перспектива: эвристический фолбэк на случай, когда ML недоступен

Когда ни один из трёх ML-детекторов перспективы не доступен (MiDaS не развёрнут, OpenCV.js не может загрузиться, YOLO не подключён), плитки всё равно получают видимый перспективный warp:

- Когда авто-детектор ничего не вернул, углы стены берутся как трапеция из bbox маски стены (верхние углы сужены на 8% внутрь — типичный ракурс съёмки интерьера)
- UI больше не врёт «Перспектива определена автоматически», если углы получены эвристикой
- Калибровка масштаба всё ещё сеется из ширины bbox маски — плитки сохраняют правильный физический размер
- Реальные детекторы (когда появятся) перекрывают эвристику, никаких симптоматических правок не требуется

**Design-doc:** [`docs/design-docs/AUTO-PERSPECTIVE-FALLBACK-STRATEGY.md`](./design-docs/AUTO-PERSPECTIVE-FALLBACK-STRATEGY.md) — полный разбор текущего pipeline, почему каждая из трёх стадий не работает в dev-окружении, и roadmap (deploy MiDaS / OpenCV Worker / downsampling / гранулярные селекторы).

### Фоторедактор стен: честная перспектива и автоопределение

Большой этап работы над перспективой стены на фото: от срочного фикса визуальной регрессии до авто-определения углов и калибровки. Выкатывалось в несколько независимых релизов.

**Исправление визуальной регрессии:**
- Панели в режиме перспективы снова показывают реальный дизайн с искажением под углом стены — ранее на их месте отображалась сплошная цветная заливка без текстуры

**Настоящий mesh-warp для перспективы:**
- Каждая панель в перспективе рендерится как искажённый quad через сетку 8×8 треугольников с кусочно-аффинным преобразованием — края ровные, без швов и алиасинга
- Добавлен кэш warped-изображений: повторный рендер той же панели в той же перспективе мгновенный
- Подстройка яркости панели под освещение стены перенесена внутрь warp-рендерера — корректнее работает с цветными оттенками

**Связка калибровки с раскладкой в перспективе:**
- Размеры панелей в перспективе теперь действительно соответствуют физическим сантиметрам: панель 30×30 см при калибровке через розетку имеет правильный размер в любом углу стены
- Авто-заполнение стены учитывает перспективу: проверка «помещается ли панель» идёт по quad-форме, а не по bounding-box — меньше ложных отказов у границ стены
- Авто-заполнение блокируется, если калибровка не выполнена — вместо расстановки «на глаз» показывается подсказка откалибровать масштаб

**Авто-определение перспективы:**
- При загрузке фото система автоматически ищет прямые линии (плинтусы, карнизы, стыки потолка) и на их основе вычисляет углы перспективы стены
- Если уверенность распознавания высокая — углы подставляются автоматически, пользователю остаётся только подтвердить или подправить
- Если линий мало (пустая однотонная стена) — показывается подсказка отметить углы вручную
- Баннер «Перспектива определена автоматически» с кнопкой «Сбросить» для отката к ручному режиму

**Авто-определение масштаба по эталону:**
- На фото автоматически детектируются ориентиры известного размера (розетка ~8,5 см, выключатель, плинтус) и по ним рассчитывается пикселей на сантиметр
- Пользователь видит список найденных эталонов и может переключиться между ними
- Если эталон не найден — автокалибровка пропускается, остаётся ручной режим

**Сохранение на сервере:**
- Углы перспективы и параметры калибровки теперь сохраняются в проекте на бэкенде — при повторном открытии проекта они восстанавливаются точно как были
- Отдельные эндпоинты частичного обновления перспективы и калибровки: drag угла → debounce ~1 с → PATCH без пересылки всего проекта
- Оптимистичная блокировка по версии: если в двух вкладках одновременно редактировать один проект, вторая получит понятное сообщение «данные изменились, обновите страницу» вместо тихого затирания

**Инфраструктура:**
- В проект добавлены миграции БД (Alembic) — теперь изменения схемы накатываются и откатываются одной командой вместо ручной правки PostgreSQL
- Заложен фундамент для авто-перспективы на пустых стенах через анализ глубины ML-моделью на бэкенде (ядро готово, подключение к пользовательскому интерфейсу — следующий этап)

**Стабилизация после код-ревью:**
- По итогам аудитов каждой из фаз закрыто более 40 пунктов технического долга: согласованы имена, устранены дубликаты, добавлена защита от гонок между вкладками и потоками, расширено покрытие тестами
- Добавлены тесты для всех новых модулей: mesh-warp математики, quad-coverage, детекторов перспективы и эталонов, персистентности углов на бэкенде, частичных PATCH-эндпоинтов

**Авто-перспектива: backend-first для надёжного определения стены:**
- Основной путь распознавания стены переключён с клиентского OpenCV на серверный depth+RANSAC — работает устойчиво даже на однотонных стенах без видимых линий (плинтусов, карнизов), где Hough-детектор ничего не находил
- Новый inline-эндпоинт принимает фото и маску стены прямо в теле запроса — распознавание срабатывает **сразу после загрузки фото**, до сохранения проекта; раньше приходилось сначала сохранять проект, чтобы запустить фоновый анализ
- OpenCV-распознавание остаётся как резервный путь (offline-режим, недоступность сервера) — 11 МБ WASM-бандла больше не грузится на критическом пути первого показа
- Устранён «вечный» спиннер «Определяем углы стены…»: гарантированный переход в готовое состояние в течение 15 секунд независимо от сетевых и рантайм-ошибок
- Backend возвращает также габариты стены в пикселях — фронтенд использует их для подстановки плейсхолдер-калибровки (3 м по ширине как безопасное значение для показа масштабной шкалы); честный режим: авто-заполнение панелями по-прежнему требует ручной двухточечной калибровки

**Тесты нового пайплайна:**
- Backend: happy-path для inline-эндпоинта, требование авторизации, валидация размеров маски, error-envelope для недоступного depth-бэкенда, форма ответа с bbox_pixels
- Frontend: сериализация snake_case в теле запроса, маппинг 422/plane_fit_failed и 503/depth_unavailable в типизированную ошибку, дефолтные значения bbox при обратной совместимости

**Панели теперь ложатся по перспективе стены автоматически:**
- Раньше при быстрой загрузке фото и клике «Заполнить стену» плитки ложились плоской сеткой, даже когда чуть позже приходил результат распознавания перспективы — панели уже были размещены в photo-space без искажения
- Теперь авто-калибровка из детектированной ширины стены заменяет upload-плейсхолдер и помечается как доверенная (маркер `wallWidthCm`), что снимает блок `AutoFillBlockedError` для перспективного авто-заполнения
- При завершении распознавания, если уже есть расставленные панели одного дизайна (подпись автозаполнения), раскладка автоматически пересчитывается под обнаруженную геометрию — пользователь видит, как плитки «встают» по стене без повторного клика
