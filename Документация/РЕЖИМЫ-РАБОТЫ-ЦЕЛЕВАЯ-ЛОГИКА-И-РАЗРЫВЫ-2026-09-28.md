# Целевая логика трёх режимов и обнаруженные разрывы

Дата проверки: 28.09.2026. Область: наблюдаемое меню режимов Promto + проект `/home/user/wonder-wow-wall`. Это **предложение к продуктовой логике**, а не констатация внедрённого автомата. Мы не имеем исходного кода платформы Promto; нельзя утверждать, что все платформенные механизмы отсутствуют только на основании этого проекта.

## 1. Формулировка заказчика и необходимое уточнение

Тезис «у клиента есть три режима» верен на уровне UI: скриншот показывает **Чат** («Ответ и чтение. Без изменений»), **План** («План и .md. Без запуска»), **Агент** («Код, запуск, публикация»). Пять этапов изменения файла — внутренний pipeline, а не пять режимов интерфейса. В этом смысле модель понятна.

Однако формула «Агент всегда сразу коммитит и выкатывает на прод» **не следует из надписей интерфейса и опасна как безусловное правило**. В режиме «Агент» бывают анализ текущего проекта, создание документа, локальный прототип, отладка без доступного production и незавершённая проверка. Безусловная выкладка может отправить чужие незавершённые изменения и поломать сайт. Безопасное целевое правило: **для явно запрошенного изменения боевого продукта Агент по умолчанию ведёт задачу до коммита, релиза и проверки, если пользователь не ограничил объём; при препятствии останавливается и выдаёт частичный статус, а не имитирует завершение**. Для вопросов/аудита/ТЗ публикация не нужна. Если продукт хочет default auto-deploy, это должно быть явной настройкой проекта/разрешением с защитными проверками, видимой пользователю.

## 2. Желаемый контракт по режимам

### Чат → решение, без изменения файлов
- Исследует и объясняет; указывает, что проверено, что гипотеза, и какие сведения устарели.
- Не меняет файлы, не запускает релиз, не выдаёт коммит/публикацию за результат ответа.
- При необходимости предлагает «перейти в План» или «перейти в Агент»; автоматическое переключение допустимо только при согласованном поведении UI.

### План → исполнимое ТЗ, но без запуска
- Создаёт один `.md` с исходным запросом, областью, файлами/данными, зависимостями, шагами, тестами, acceptance criteria, рисками, откатом, способом определить уровень готовности.
- Не правит runtime-код и не публикует приложение.
- Целевое дополнительное правило: коммитить **только свой план**, если план хранится в Git-репозитории. Но скриншот обещает лишь «План и .md. Без запуска»; автоматический коммит плана не подтверждён и должен быть отдельно задокументирован/реализован.
- Запуск плана в режиме «Агент» должен передавать неизменённые требования и путь к версии плана; при конфликте с новой просьбой — согласовать расхождение.

### Агент → выполнение определённого объёма
1. Зафиксировать задачу, target repo, целевой route/сценарий, разрешена ли публикация; если запрос явно ограничен локальной работой, не публиковать.
2. Проверить чистоту рабочего дерева; **не коммитить `git add -A` чужие правки** в грязном репозитории. При пересечении файлов отделить свои hunks или согласовать scope.
3. Выполнить правки и тесты; проверить runtime и запрошенный сценарий локально.
4. Сохранить относящиеся к задаче изменения в Git-коммите. Если не удалось — явно сообщить причину, а не оставить бесконтрольное `??`.
5. Для боевого изменения при согласованной публикации: собрать **из определённого коммита/снимка**, сохранить резервную версию, выложить атомарно, выполнить необходимые миграции с отдельным планом, проверить публичные зависимости и пользовательский путь. Избегать ручной правки хешированного JS и смешения старого entry graph с новой сборкой.
6. Записать release record: commit, fingerprint сборки, адрес среды, время, затронутые сервисы/миграции, доказательства публичной проверки и путь отката. Финальный статус — «проверено на проде» только после end-to-end; иначе «опубликовано, не подтверждено» или «не опубликовано».

### Три видимых результата и обязательные промежуточные статусы
- ① «Исследование/ТЗ»; ② «Локально реализовано/зафиксировано»; ③ «На проде проверено».
- На переходе показывать явный статус: «заблокировано», «на проде, но сценарий не проверен», «откачено». Эти состояния не являются четвёртым пользовательским режимом, но необходимы для честной отчётности.

Это **не** доказательство, что функция не работает; это непроверенный gate.

## 4. Порядок устранения без потери пользовательских правок

1. Сначала построить карту задач → локальные файлы/коммиты → активные production assets/patches → публичный сценарий и уровень доказательств. Не использовать «на проде» только по имени коммита.
2. Для каждого открытого изменения составить отдельный scope и коммит; перед staged-операцией проверить чужие незавершённые изменения. Временные build/artifact folders классифицировать, не удалять без согласия/проверки владельца.
3. Устранить разрыв в доставке видео и провести воспроизводимую сборку сайта из фиксированной версии, не затрагивая несвязанные функции; проверить MIME, версию entry graph, логи и пользовательские маршруты.
4. Заменить ручные патчи на релизный артефакт; сохранить backups и безопасный откат. Отдельно подтвердить `/pricing`, главную, `/simple` и админский flow, если доступен законный авторизованный вход.
5. Ввести запись результата по каждой задаче: `scope`, `commit`, `build fingerprint`, `deployed?`, `public flow checked?`, `blocked reason`, `rollback reference`. В UI различать «локально», «выкладка», «проверено», а не выводить одну универсальную галочку.

**Статус документа:** аудит и предложение; он не меняет режимы платформы, не создаёт релиз и сам по себе не подтверждает корректность продакшена.
