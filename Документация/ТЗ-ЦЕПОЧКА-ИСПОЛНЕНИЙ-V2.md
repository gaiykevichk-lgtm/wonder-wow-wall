# Доработка цепочки исполнения — V2

## Статус и основание

15.09.2026. Анализ текущих исходников и замечаний пользователя. Это план недостающей реализации, не отчёт о выполненной функции. Production в рамках этого анализа не изменялся. Сохраняет требования первого ТЗ, но отменяет вложенную таблицу как основной способ просмотра: фактуры и фотографии должны оставаться видимыми без раскрытия.

## Подтверждённые пробелы

1. PanelTextureAssignment даёт явное подключение фактуры к панели, но назначение не создаёт удобный следующий шаг — отдельное исполнение.
2. PanelVariant уже имеет постоянный ID, panel_id, texture_id и две галереи. Эту сущность следует использовать для одного исполнения, а не вводить параллельную дублирующую сущность.
3. AdminPanelsWizard.handleSave создаёт одну запись на ячейку размер×фактура и складывает все её фотографии в image_paths. Пользователь не может явно отделить несколько исполнений от нескольких ракурсов одного исполнения.
4. У PanelVariant нет названия/номера исполнения. Поля color_id/color_hex сохранены, но мастер отправляет null; комментарии доменной модели объявляют цвет устаревшим.
5. CatalogPanelPage формирует выбор через изображения группы и finishIndex, а не устойчивый ID исполнения. Исправлять только админку недостаточно.
6. Кнопки общих справочников не заменяют управление цепочкой. Они дублируют существующие вкладки и не являются выполнением требования.
7. Предыдущая экспериментальная AdminPanelMatrix сводила варианты в Map по panel_id:texture_id и скрывала часть записей. Не использовать её как источник истины.

## Семантика

Базовая форма/существующая размерная позиция → подключённая фактура → N самостоятельных исполнений → собственные фотографии исполнения и собственные фотографии в дизайне.

Исполнение — не фотография и не цвет сам по себе. Несколько ракурсов могут принадлежать одному исполнению. Несколько исполнений могут иметь одну фактуру и одинаковый цвет. Цвет необязателен. Фото в дизайне принадлежит только variant_id, не форме, не фактуре и не позиции картинки в массиве.

Пример только для объяснения, не для наполнения каталога: одна форма, фактура «Текстиль», два исполнения с разными названиями/цветами; у каждого свои товарные и интерьерные фотографии.

## Данные и API

- Сохранить PanelVariant и существующие ID/URL.
- Additive migration: добавить название исполнения, порядок отображения; цвет поддержать в create/update/UI как необязательную характеристику. Не делать цвет обязательным или уникальным ключом.
- На одну пару panel_id+texture_id разрешены несколько variant_id. Проверить реальные ограничения БД и репозитория до миграции.
- Проверять родительскую панель, текстуру и активное назначение при создании. Отключённое назначение не уничтожает исполнения и фотографии.
- Отдельное создание исполнения в контексте выбранной пары; атомарное сохранение названия, цвета, статуса и обеих галерей.
- Отмена редактора не меняет сохранённые данные. Для параллельных правок — проверка версии/updated_at и явный конфликт.
- Серверные фильтры по панели, фактуре и активности, серверная пагинация; не ограничивать каталог первыми 100/200 записями.
- Аудит создания, изменения, отключения и удаления исполнения с actor, before/after.

## Админка

Оставить обзорную плоскую таблицу. Одна конечная строка — одно исполнение. Колонки: форма и размер; фактура с образцом; название/цвет исполнения; фото исполнения; фото в дизайне; статус; действия.

- Никаких обязательных раскрытий для просмотра фактур и фотографий.
- Назначить фактуры: выбрать существующую форму, галочки фактур, сохранить; видимость форм без исполнений обязательна.
- У каждой пары форма×фактура действие «+ Исполнение» с уже выбранными родителями.
- В модалке исполнения: название, необязательный цвет, товарная галерея и отдельно галерея в дизайне. Не использовать общий мастер с одной фотоячейкой на фактуру для создания нескольких исполнений.
- Карандаш конкретной строки открывает именно её variant_id. Фото и пустое состояние «Нет» видны в таблице.
- Назначенная фактура без исполнений: «Исполнений нет» и «+ Исполнение»; не создавать фиктивный товар автоматически.
- Отключённые записи доступны модератору через фильтр и не исчезают бесследно.
- Массовые назначения сохранить как отдельное действие; общие редакторы справочников не выдавать за управление цепочкой.

## Витрина

Выбор: фактура → список исполнений по variant_id → галерея выбранного исполнения. Основное изображение — первое image_paths этого исполнения, остальные — его ракурсы. Интерьеры — только design_image_paths того же variant_id. Корзина хранит тот же ID. Название/цвет показываются вместо индекса картинки. Сохранить существующие мобильные и десктопные требования и формат заголовка шага 2.

## Существующие данные

Не разбивать существующие image_paths автоматически: невозможно узнать, где ракурсы, а где разные исполнения. Каждая существующая запись остаётся одним исполнением со всеми прежними фото. Не переносить интерьерные фотографии между исполнениями по предположению. Для неоднозначных старых галерей предусмотреть явное ручное разделение модератором с выбором принадлежности интерьерных фото и подтверждением. Имена существующих товаров не менять; отсутствие имени исполнения отображать техническим номером/ID до редактирования.

## Приёмка

Изолированные тесты (никаких выдуманных товаров в production):
1. Одной форме назначить две фактуры; одной фактуре создать два исполнения.
2. Каждому исполнению назначить несколько товарных фото и разные фото в дизайне; проверить сохранение после повторного запроса.
3. Изменить/отменить изменения второго исполнения: первое не меняется.
4. Проверить одинаковые цвета у разных исполнений и отсутствие цвета.
5. Проверить пустые назначения, отключение/повторное включение без потери фото.
6. Витрина: оба исполнения выбираются отдельно, интерьеры и ID корзины соответствуют выбору.
7. Пагинация за первой страницей, фильтры, конфликт двух редакторов, аудит.
8. Визуально проверить обзорную таблицу с фото и пустыми состояниями, открыть правильные модалки.
9. После build проверить содержимое релизного entrypoint, затем хеши опубликованных assets; HTTP 200 не считать проверкой сценария.

## Дополнительная диагностика заказа

Подтверждён второй критический разрыв: CheckoutPage.handleSubmit не вызывает API заказа, генерирует случайный WW-номер и очищает корзину. Требуется реальная транзакционная отправка и обработка ошибок без очистки корзины до подтверждения сервером. Адрес сейчас одно текстовое поле, API ожидает city/street/building; нельзя выдумывать адресные поля при адаптации. Проверить также оплату, доставку и итоговую сумму: локальный total с доставкой не равен серверной сумме позиций.

Подтверждён разрыв PDP: getTextureGroups делает unique(flatMap(image_paths)), selectedVariant индексирует другой массив variants с clamp. Две фотографии одного variant могут выглядеть как два исполнения, но дать один ключ корзины. Это не только ошибка надписи.

Начата, но не завершена реализация: additive поля variant_id/execution_name на OrderItem, запросах и ответах заказа, ORM и сериализации админки; миграция 023 после локальной 022. Миграции не применены, production не менялся. Эти поля пока не означают корректное оформление: необходимы проверка соответствия сборки на сервере, PDP/cart/checkout wiring и тесты.

Критерий полной приёмки: два разных исполнения одной фактуры одной панели сохраняются в двух отдельных строках корзины и заказа; каждое содержит базовую панель, фактуру, размер, устойчивый ID исполнения, снимок названия и изображения. Повторное добавление той же сборки увеличивает только её количество. Переименование/перестановка галереи после заказа не меняет сохранённую спецификацию. Нельзя считать факт появления номера заказа доказательством сохранения в БД.

## Релиз V3 — 15.09.2026 18:30 UTC

Реализована сквозная идентификация комплектации заказа. Миграции 022 (panel_variants.name) и 023 (order_items.variant_id, execution_name) применены: alembic_version = 023. 10 существующих panel_variants получили пустое имя; админ сможет присвоить читаемые имена отдельно.

Транзакционная защита заказа:
- валидация: variant_id обязателен;
- проверка: variant существует и активен;
- проверка: variant.panel_id == design_id;
- проверка: variant.texture_id совпадает с присланным;
- авто-снимок имени из БД, если фронт не прислал.
Эти правила подтверждены изолированными тестами в Python против реальных use cases.

PDP-логика: каждая кнопка фактуры показывает ровно столько миниатюр, сколько уникальных ракурсов есть в её вариантах; сами варианты не сжимаются в общий массив. Идентификатор `selectedVariant.id` уникален на фактуру, поэтому две разные выборы дают две разных строки в корзине (id = `exec-${variant.id}-${size.key}`).

CheckoutPage.handleSubmit реально вызывает useCreateOrder; ошибки сервера сохраняют корзину; адрес разбирается на city/street/building; при ошибке авторизации отправляет на /login. После успешной реальной публикации экран показывает серверный номер (не случайный WW-), без очистки корзины до фактического ответа сервера.

Админ заказа: состав заказа показывает размер, фактуру, имя исполнения (или fallback по ID), короткий variant_id префикс и количество.
