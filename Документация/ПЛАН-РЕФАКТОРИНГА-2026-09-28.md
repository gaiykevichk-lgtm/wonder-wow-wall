**Статус:** план, не реализация. **Дата:** 2026-09-28. **Локальная база:** `master`, HEAD `1c7ec52` на момент исследования; перед каждой фазой перепроверить HEAD и `git status`. Проект активно меняется, не применять план к иной версии без актуализации. **Масштаб:** фронтенд React/Vite/TS, FastAPI/DDD, админка, PostgreSQL/Alembic, S3/медиа, интеграции, окружение. Продакшен и данные не менялись в рамках составления плана.

## 0. Цель, границы и правила

Цель — сделать код поддерживаемым, контракт API проверяемым, изменения безопасными, уменьшить рост локального окружения **без удаления нужных функций, пользовательских данных и production persistence**. Это НЕ миграция стека, НЕ новый продукт и НЕ предложение выключить авторизацию, заказы, БД, S3 или админку. Сохранить текущие URL и бизнес-правила до утверждения отдельной миграции. Для новых persistent сущностей — PostgreSQL через `DATABASE_URL`; не использовать SQLite как fallback проекта. Документы `AGENTS.md`, `frontend/CONVENTIONS.md`, `backend/CONVENTIONS.md` задают текущие соглашения; при их изменении сначала согласовать обновлённые правила с фактическим кодом. Историческая `Документация/STATUS.md` и README содержат устаревшие утверждения; сверять с кодом и ТЗ, не принимать старые ✓ как критерий готовности.

**Не смешивать:** 1) рефакторинг при сохранении поведения; 2) исправление обнаруженных дефектов; 3) исполнение незакрытых продуктовых требований (`Документация/АУДИТ-ТЗ-2026-09-24.md`). Для каждого PR/этапа фиксировать категорию, baseline, тесты и откат. Отдельные миграции данных и изменения API — только с backward-compatible rollout и резервной копией. Не предпринимать автоматического деплоя. Существующие библиотеки (FastAPI, SQLAlchemy/Alembic, TanStack Query, React Testing Library, Vitest, AntD) покрывают большинство задач; новый framework/DI/генератор клиентского кода не вводить без сравнения затрат и проверки совместимости.

## 3. Порядок, объём и ограничения

```text
A baseline → B конкретные P0 → C migrations/media → D critical backend/business
                                          ↘ E admin по экрану → F другие UI/ML → G стабилизация
```

Некоторые работы C (миграции) и D (сессии/заказы) требуют отдельного согласования модели данных и доступа к staging; их нельзя «закрыть» только unit-тестами. E и F можно частично вести после B параллельно с независимыми областями, но менять API-схему одновременно с DB cutover нельзя без координации. Каждый рабочий PR ограничивать одной проверяемой областью, малым diff и тестом на заявленный сценарий. Приоритет этапа определяется риском потери данных/доступа, а не строками кода.

**Критерий завершения всего плана:** у каждого flow есть опубликованный контракт и ответственный источник данных, миграции проходят на PostgreSQL-копии, интеграции S3 и авторизация проверены фактическими сценариями, заказ и админский CRUD не деградировали, TypeScript/build/test/визуальные проверки после последнего изменения завершились успешно, известные исключения оформлены явно. До этого статус — частичный.

## 4. Что делать первым практически

1. В маленьком PR восстановить проверку типов и красные адресные тесты **после классификации ошибок**; отдельно исправить `RecommendationFilters` с API тестом.
2. Параллельно *без записи в production* проверить граф Alembic, текущую версию PostgreSQL, OpenAPI/admin route map и выдачу медиа, включая read-after-upload на staging. Перед миграцией или изменением хранилища нужен snapshot и сценарий отката.
3. После P0 выбрать первую вертикаль для инкрементального рефакторинга: `Админка: исполнение/фото → API → SQL/S3 → публичная карточка`, поскольку в ней пересекаются основные риски. Следующая — `Цена → корзина → заказ`.

**Запрещённые shortcuts:** `git clean -fdx`, массовый `git add -A` в корне `/home/user`, reset пользовательских правок, удаление кэша без проверки, выключение S3/БД/ML/оплаты, переписывание роутов без алиасов, перегенерация миграций поверх production, выдача mock за production-ready persistence.
